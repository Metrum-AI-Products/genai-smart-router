# Issue #507 handoff

## Outcome

Implemented a scoped, non-serving migration-framework foundation for durable usage data, followed by a guarded usage-schema baseline adoption increment. It provides immutable checked-in migration definitions, checksum validation, a normalized relational ledger, schema/data compatibility ranges, durable per-scope leases, safe status/plan/verify/apply entrypoints, and a `router-migrate` CLI. The framework fails closed for an applied checksum mismatch or unknown future migration ID.

The usage manifest now contains immutable migration `2026071901` (schema version 1, data version 0). It adopts an already initialized legacy usage schema only after checking that every current relational usage table exists, has columns, and contains no prohibited JSON/array type. It writes no application-table DDL or data. An empty database refuses adoption and leaves no ledger record. `router-migrate --action=verify` now rechecks applied migration postconditions rather than acting as a status alias.

The legacy usage-store initializer still uses `AutoMigrate`; it has **not** been converted to explicit ordered DDL definitions in this slice. Fresh installs remain on that initializer until the full reviewed replacement lands. This change deliberately does not enable serving-process automatic migration.

## Unresolved risks and questions

- Full acceptance requires replacing the very large existing `usageStore.migrate()` AutoMigrate/backfill path with reviewed, ordered historical DDL/data definitions and fixtures. The adopted baseline does not prove individual legacy-column/index/constraint parity beyond table/column presence and relational-type safety; a full manifest must add exact postconditions.
- The durable lease is relational and tested for SQLite contention. PostgreSQL advisory-lock implementation, lock/statement timeout configuration, and non-transactional/concurrent-index recovery still need dedicated definitions and integration tests.
- Failed migration entries, resumable data-job checkpoint records, startup policy/readiness integration, metrics/dashboard, signed-state format conversion, release-note generation, and all cross-version rolling-upgrade fixtures remain unimplemented.
