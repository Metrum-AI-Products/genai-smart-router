# Harbor Agentic Coding Case Study

This case study evaluates model groups behind GenAI Smart Router using Harbor and real coding agents. Each run used a router token scoped to one `{agent, model_group}` pair so usage and cost signals could be compared cleanly.

The model group names in this case study are historical deployment-specific names from the benchmark environment. GenAI Smart Router does not require names such as `default`, `fast`, `small`, `medium`, `high`, or `big-coder`.

## Task

- Dataset/task: `aider/polyglot_python_two-bucket`
- Goal: implement `two_bucket.py` so the verifier accepts the bucket-measuring algorithm and required `ValueError` behavior.
- Agents: Codex CLI and Claude Code CLI.
- Hosted router endpoint: Metrum GenAI Smart Router.

## Reward Score

Harbor reports `1.0` when the submitted artifact passes the verifier for the task. A score of `0.0` means the verifier rejected the artifact. Agent runtime exceptions are tracked separately because an agent can produce a passing artifact but still exit nonzero.

## Model Groups Evaluated

| Group | Intended use |
|---|---|
| `default` | General-purpose route |
| `fast` | Lower-latency, budget-aware route |
| `small` | Lower-cost route for simple work |
| `medium` | Balanced development route |
| `high` | Stronger route for complex work |
| `big-coder` | Coding-oriented agent route |

The evaluated routing policy used validated tool-capable targets from OpenRouter, MiniMax, Moonshot/Kimi, and low-weight compatible fallback paths where configured.

## Models Used

| Provider route | Provider model | Role in study |
|---|---|---|
| MiniMax | `MiniMax-M3` | High-weight coding-capable target and tool-compatible route |
| Moonshot AI / Kimi | `kimi-k2.7-code` | Direct coding target for Claude Code-compatible tool flows |
| OpenRouter | `deepseek/deepseek-v4-flash:nitro` | High-throughput Nitro target used across general and tool-capable groups |
| OpenRouter | `google/gemma-4-26b-a4b-it:nitro` | Validated secondary Nitro target in general/tool-capable routes |
| OpenAI-compatible fallback | `gpt-5.4-nano` | Low-weight non-tool fallback path where configured |

The point of the benchmark is not just "which model passed." It measures whether model groups can hide provider complexity while still exposing the numerical signals needed for routing and cost decisions: pass rate, latency, token volume, upstream attempts, fallback count, cache behavior, and token throughput.

Agentic coding workloads are token-heavy because the agent repeatedly reads context, reasons about files, calls tools, observes output, and updates artifacts. The router's tokenomics view is therefore central to cost governance: the same task can pass across model groups while consuming materially different token budgets and wall-clock time.

## Case Study #2: Go Sublist On Hosted Default Route

The second benchmark used the same hosted Metrum endpoint and the same pricing assumptions, but narrowed the routing policy under test to the `default` model group. Each agent used a separate one-use case-study router token so production usage could be attributed by internal key, client, model group, provider model, and caller IP.

### Task

- Dataset/task: `aider/polyglot_go_sublist`
- Goal: implement `/app/sublist.go` so the Go verifier accepts `Sublist(l1, l2 []int) Relation`.
- Required behavior: return `equal`, `sublist`, `superlist`, or `unequal` for two integer lists, treating sublists as contiguous sub-sequences.
- Agents: Codex CLI and Claude Code CLI.
- Router model group: `default`.
- Case ID: `harbor-go-sublist-default-20260615T063200Z`.

## Interpretation

Every final published run passed with reward `1.0`, which means the routed model groups were able to complete the coding tasks under both Codex CLI and Claude Code CLI. The report also shows why model-group evaluation should include more than pass/fail status: elapsed time, tokens, fallbacks, provider mix, cache eligibility, caller IP, and throughput vary materially by task, agent, and group.

For production buyers, the key result is that GenAI Smart Router gives a single integration point plus evidence for routing policy. A platform team can compare groups using task success, cost drivers, throughput, fallback rate, and cache eligibility before deciding which model group each user, project, or workload should be allowed to call.
